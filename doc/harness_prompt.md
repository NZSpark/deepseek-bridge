构建模块化、持久化、可持续维护的 Agent Harness

请基于当前项目，设计并搭建一套模块化、文件驱动、跨工具兼容、可长期复用的 Agent Harness（智能体运行框架）。

核心目标：通过持久化记忆、模块化 Skills、渐进式上下文加载、自动状态维护和定期 Cleanup，实现跨会话连续工作，降低 Token 消耗，提高执行效率、结果质量及长期可维护性。

一、核心架构

1. Persistent Memory（持久化记忆）

* 使用本地 Markdown 文件持久化项目知识、规则、决策、任务状态及历史经验。
* 建立清晰的文件层级、索引及引用关系，避免信息散落和重复存储。
* 区分长期稳定知识、关键约束、决策历史、当前状态与临时任务信息。
* 不依赖单次会话上下文，支持新会话快速恢复工作状态。

2. Modular Skills（模块化技能）

* 将不同工作流封装为独立、可组合、可维护的 Skills。
* 每个 Skill 明确定义适用场景、触发条件、输入输出、操作步骤和验证标准。
* 通过统一入口和索引进行发现、选择与调用。
* 优先复用现有 Skills，避免重复建设。

3. Progressive Disclosure（渐进式按需加载）

* 采用轻量级入口文件和分层 Markdown 索引。
* 启动时仅加载必要的核心规则与当前状态。
* 根据任务类型精准路由，按需读取对应 Skills、知识和历史记录。
* 避免全量加载、重复读取和无关上下文注入。
* 对读取内容建立优先级、依赖关系及 Token 预算。

4. Cross-Tool Compatibility（跨工具兼容）

* 核心知识、业务规则和工作流尽可能采用工具无关的 Markdown 格式。
* 支持 Claude Code、Codex 等工具共享同一套核心知识和流程。
* 针对不同工具设置轻量适配入口，例如 CLAUDE.md、AGENTS.md。
* 避免为不同工具重复维护内容相同的独立知识库。
* 明确共享文件的写入规则，防止不同工具造成状态冲突。

二、记忆与状态管理

5. Memory Architecture（分层记忆架构）

根据实际需求设计或复用以下逻辑模块：

* CRITICAL.md：不可违反的核心约束、高优先级规则及必要入口。
* state.md：当前任务、最新进展、阻塞问题和下一步行动。
* DECISIONS.md：关键决策、理由、状态及变更历史。
* memory/：长期知识、历史经验与项目背景。
* skills/：可复用的标准化工作流。
* index.md：知识索引、任务路由与按需加载入口。
* archive/：过期、被取代及历史参考内容。

以上仅为逻辑参考，优先适配现有项目结构，不要求机械创建所有文件或目录。

6. Continuous Memory Update（持续记忆写回）

* 每次重要任务完成后，更新对应状态、决策与知识文件。
* 将经过验证、具有长期价值的信息沉淀到持久化记忆中。
* 临时过程信息不直接进入核心记忆。
* 更新时优先修改现有记录，而不是无限追加。
* 确保新会话能够准确识别当前进度、历史决策及下一步任务。

三、Cleanup：记忆生命周期管理

7. Memory Cleanup & Consolidation（定期清理与整合）

建立独立、可复用的 Cleanup Skill，并纳入 Harness 的日常运行机制。

定期扫描项目记忆及状态文件，执行：

* Stale Detection（过时检测）：识别已经过期、不再适用或被新决策取代的信息。
* Deduplication（去重）：合并重复知识、重复规则、重复决策说明与冗余描述。
* Consolidation（知识整合）：将零散但相关的信息整合为简洁、结构化、可引用的知识。
* Archiving（历史归档）：将不再需要频繁加载、但仍有参考价值的内容移入 archive/。
* Conflict Detection（冲突检查）：检测相互矛盾的规则、状态和决策；能通过明确的新旧关系解决的予以标记，无法确定的提交人工确认。
* Critical Pruning（核心约束精简）：保持 CRITICAL.md 只包含真正关键且当前有效的规则，避免持续膨胀。
* State Compaction（状态压缩）：定期整理 state.md，仅保留当前进展、有效阻塞、待办事项及恢复工作所必需的信息。
* Index Maintenance（索引维护）：同步修复索引、引用路径和路由关系，防止归档后出现断链。

Cleanup 执行原则：

1. 优先合并、压缩和归档，而不是直接删除。
2. 历史关键决策保留可追溯记录，不能因为新决策出现就静默覆盖历史事实。
3. 对涉及核心规则、重要决策或存在歧义的信息，不得未经确认进行不可逆修改。
4. 清理过程应记录变更摘要、原因及受影响文件，必要时支持回滚。
5. Cleanup 后重新验证索引完整性、规则一致性和上下文加载效率。
6. 避免为 Cleanup 本身增加过度复杂的机制。

Cleanup 触发机制：

* 日常轻量清理：重要任务完成、状态写回时触发。
* 周期性深度清理：按可配置周期或文件规模阈值触发。
* 上下文优化清理：核心文件超过设定 Token 预算时触发。

如运行环境支持自动调度，可配置定期执行；否则将 Cleanup 纳入现有工作流的执行节点，并提供可手动调用的入口。

四、效率、质量与可靠性

8. Context & Token Optimization（上下文效率）

* 最小化启动上下文，只加载当前任务真正需要的信息。
* 建立分层索引、精准路由、按需读取及上下文压缩机制。
* 减少重复规则、重复说明及跨文件信息冗余。
* 避免过度工程化，以实际 Token 效率和任务质量为优化依据。

9. Validation & Reliability（验证与可靠性）

* 为关键工作流建立必要的检查和验证步骤。
* 确保任务结果、持久化状态及关键决策相互一致。
* 重要写入和 Cleanup 操作应具备审计记录及合理的恢复机制。
* 防止跨工具并发写入造成记忆覆盖、状态错乱或规则冲突。

10. Continuous Improvement（持续迭代）

* 记录长期重复出现的问题、有效解决方案及经验教训。
* 定期评估 Skills 的有效性、上下文消耗和执行质量。
* 将经过验证的改进整合回现有 Skills 和知识库。
* 保持架构简单、模块边界清晰、升级和维护成本可控。

五、实施要求

先审查，后设计，再实施。

1. 检查项目现有目录、规则、Skills、知识文件及工作流。
2. 识别已有机制、重复内容、结构问题及真正需要补充的能力。
3. 优先复用现有结构，不随意推倒重建、不制造平行的重复系统。
4. 设计最小必要架构，明确入口、索引、记忆分层、Skills 路由、状态写回及 Cleanup 机制。
5. 在不破坏现有项目的前提下完成搭建或优化。
6. 验证跨会话恢复、按需加载、工作流调用、记忆写回及 Cleanup 的实际效果。
7. 输出最终架构说明、关键文件职责、调用方式、维护机制及验证结果。

最终验收标准：

新会话或不同 AI 工具进入项目后，能够通过最小必要上下文，快速理解项目关键约束和当前状态，精准调用所需知识与 Skills，可靠完成任务并写回有效记忆。

系统能够长期运行，通过持续更新、去重、压缩、归档和 Cleanup，控制核心上下文规模，避免知识库无序膨胀，同时保留重要决策和历史信息的可追溯性。

最终实现：高复用、低冗余、低 Token 消耗、跨工具协作、长期可维护的 Agent Harness。
