# 提示词结构设计

本文规定发往网页版模型的**单轮输入文本**的组装规则。目标是把「用户要什么」
「工具执行出了什么」「怎么调用工具 / 有哪些行为约束」三件事在文本里**分区、有序、
可缺省**地表达，让模型不会把历史、格式说明或工具结果误当成本轮任务。

## 1. 三部分定义

一轮输入文本由至多三个区段组成，**顺序固定**：

| 序号 | 区段名 | 来源 | 语义 |
| --- | --- | --- | --- |
| 1 | `[用户问题]` | 最后一条 `role=user` 消息，**仅当其尚未提交** | 本轮要做什么 |
| 2 | `[工具调用结果]` | 该 user 之后的**最新一组** `role=tool` 消息 | 上一步工具真正返回了什么 |
| 3 | `[运行环境与要求]` | 客户端 system/developer 约束 + `_PREAMBLE` + `format_tool_instructions(tools)` | 身份说明、行为约束、工具格式契约 |

三部分**不嵌套、不交错**：先 1，再 2，最后 3。

**但第 1、2 部分语义互斥，常规请求不会同时出现。** 有工具结果说明用户指令已提交、
无需重发；没有工具结果说明尚无执行、没有结果可报。详见 6.1。

### 1.1 `[运行环境与要求]` 的组成

第 3 部分由三块内容按序拼成（每块可缺省）：

1. **客户端约束**：客户端发来的 `role=system` / `role=developer` 消息，经
   `strip_harness_sections` 剥离脚手架、`neutralize_system_prompt` 中性化之后剩下的文本。
2. **身份说明**：`_PREAMBLE`（「你是一个大语言模型…由本地客户端读取」）。
   它是常驻的身份声明，不是任务。**全局只出现一次**——system 块不再注入第二句同义
   身份（见 8.1）。
3. **工具格式契约**：`format_tool_instructions(tools)`，仅在声明了 tools 时出现。

## 2. 允许的组合

| 组合 | 场景 |
| --- | --- |
| 1 + 3 | 用户刚提问，尚无工具结果（常规首轮） |
| 2 + 3 | 工具链续跑：用户指令已提交，本轮只有工具结果（常规次轮起） |
| 1 | 无运行环境与要求（`_PREAMBLE` 关闭、无 system、未声明 tools） |
| 2 | 同上，只有工具结果 |

**1 + 2 + 3 不是常规形态。** 第 1 部分与第 2 部分语义互斥——一旦最后一条 user 之后
出现了工具结果，说明这条指令**已经提交过**，第 1 部分必须省略（见第 3 节
「提交后不重发」）。两者同时出现只可能来自「旧 tool 结果 + 一条新 user」这种畸形输入，
此时第 2 部分只取最后一条 user 之后的消息，旧结果自然被排除。

**非法形态**：只有 3。`[运行环境与要求]` 是契约与约束说明，不是任务；单独发它没有意义，
且会让模型把格式说明当成本轮内容（真实事故：解析失败的 `<tool_call>` 正文被当回答
返回后，用户补发的格式说明在下一轮被当成本轮任务发出）。

出现「只有 3」时视为输入为空，报 `InvalidRequestError`。

## 3. 组装算法

```
组装(messages, tools):
    parts = []

    # 0) 定位
    idx = 最后一条 role == "user" 的下标
    start = idx + 1 if idx >= 0 else 文末连续 tool 的起点
    results = [m for m in messages[start:] if role(m) == "tool"]

    # 1) 用户问题：最后一条 user，**但已有工具结果时省略**（提交后不重发）
    if idx >= 0 and not results:
        parts.append("[用户问题]\n" + text(messages[idx]))

    # 2) 工具调用结果：该 user 之后的全部 tool 消息
    if results:
        parts.append("[工具调用结果]\n" + join(正文(m) for m in results, "\n\n"))

    # 3) 运行环境与要求：客户端约束 + 身份说明 + 工具格式契约
    notice = []
    notice += 客户端约束(messages)      # system/developer 清洗后
    notice += [_PREAMBLE]               # 常驻身份说明
    if tools:
        notice += [format_tool_instructions(tools)]
    if notice:
        parts.append("[运行环境与要求]\n" + join(notice, "\n\n"))

    return join(parts, "\n\n")
```

规则要点：

- **用户指令提交后不得重发**。最后一条 user 之后若已存在 tool 消息，第 1 部分必须省略，
  只剩 2+3 或仅 2。真实事故：同一条用户指令被反复提交，模型以为用户又原样说了一遍。
  这是 `SiteTimeoutError` 不重试那条原则在提示词层的同一体现——提交动作只能发生一次。
- **切分点是最后一条 user**，不是最后一条 assistant。以 assistant 为界会把上一轮
  回复之后用户补发的内容（例如手动贴的格式说明）带进本轮，多轮叠加后 delta 持续膨胀
  （实测某轮达 21049 字符）。
- **工具结果必须带上**。工具链一轮的形状是 `user → assistant(tool_calls) → tool(result)`，
  最后一条消息是 tool、之后没有新 user。只发「最后一条 user」会让每轮都重发原始指令，
  工具结果永远到不了模型，模型只能反复重发同一条调用。
- **`[运行环境与要求]` 恒定包含 `_PREAMBLE`**，因此真实请求里只有「1+3」与「2+3」
  两种常规形态。`1` 与 `2` 保留为退化形态（`_PREAMBLE` 被显式关闭、无 system、
  未声明 tools 时），不是常规路径。
- **绝不出现「只有 `[运行环境与要求]`」**。

## 4. 各区段内部渲染

### 4.1 `[用户问题]`

原文照发，不做中性化、不剥离 harness 段。用户的提问就是用户的提问。

**只在最后一条 user 之后没有工具结果时出现。** 一旦有工具结果，这条指令已经提交、
已在网页会话上下文里，重发就是重复提交。

### 4.2 `[工具调用结果]`

**只保留最新一组工具结果，历史结果不重发。** 此前各轮的 tool 结果已经随各自那轮进过
网页会话上下文；再带上只会让 delta 随轮数膨胀，模型也容易把旧结果当成本轮刚发生的事。

取的是「末尾连续的 tool 段」而不是「最后一条 tool」：模型一次可以输出多个 `tool_call`
（并行调用），每个回一条 tool 消息。只取最后一条会让其余调用的结果丢失，模型只能
重新发起那些调用。

**不再逐条加 `[tool result: <name>]` 前缀**——区段标题已经说明这是什么，
逐条加前缀只会让文本变噪。工具名若对理解结果必要，由模型从上下文推断；
若后续发现需要，再以行内标注形式补回。

每条结果正文的约束：

- 经 `clip_result` 截短（上限 `TOOL_RESULT_MAX_CHARS`），截断处标注
  `[... truncated N chars ...]`，**不整块丢弃**。
- 空输出必须解释，否则模型会死循环重发同一条命令：
  `（命令已成功执行，没有产生任何输出；继续下一步即可）`。
- 多条结果之间用空行分隔（同一组并行调用的结果）。

### 4.3 `[运行环境与要求]`

三块内容按序拼接，块间空行分隔：

1. **客户端约束**：只保留真正的工作约束。`<skills>` / `<tools>` / `<rules>` / `<cwd>` /
   `<environment>` / `<docs>` / `<guidelines>` / `<system_prompt>` / `<available_skills>`
   等脚手架整块剥离；身份断言替换为中性句、能力断言删除。
2. **`_PREAMBLE`**：常驻身份说明，固定文本。
0. **语言/风格补偿句一律删除**：`Answer in Chinese.` / `Always answer in …` /
   `Respond in …` / `Be concise.` 这类指令是英文 harness 为对冲自己的英文 preamble
   加的补偿。我们的注入文本已是中性中文，再要求「用中文回答」既多余，又会被模型
   当成本轮任务的一部分复述。`neutralize_system_prompt` 用 `_LANGUAGE_STYLE_PATTERNS`
   整句删除，不动其它真实工作约束（如「用 tab 缩进」）。
3. **工具格式契约**：`format_tool_instructions(tools)`，规则见 `glm_web/tools/prompt.py`：
   - 只给一种格式并给全：`tool_call` 围栏 + 一行 JSON 示例 + 可一次输出多个 + 不需要工具就直接回答；
   - 不逐字写出目标站点的原生工具标记形状；
   - 注入点与强调点共用同一份文本，返回前统一过 `sanitize()`。

## 5. 与会话模型的关系

三部分设计成立的前提是：**网页会话本身持有更早的上下文**。
因此 `[用户问题]` 只带最后一条 user，不带历史 user/assistant；历史由网页侧负责。

若网页会话被轮转（`pending_rotation`）或首次使用（`needs_seed`），走播种路径
`seed_prompt`：完整重放历史（受 `SEED_MAX_CHARS` 预算约束，超限保头尾）。
播种是**接续上下文**，不是本设计的单轮形态；播种时同样按上述三部分结构组织，
只是第 1 部分换成完整历史摘要。

**播种不遵守 I2/I3。** 它必须重放多条 user 与多组工具结果——网页侧上下文为空，
不重放就没有上下文可接续。两条不变量保护的是「会话已建立之后的增量轮」，
播种走的是另一条路径。这也意味着 `seed_prompt` 的正确性不能靠 I2/I3 的测试推断，
需要单独的断言（见 9）。

## 6. 不变量（每一条都有对应测试）

以下四条是本设计成立的必要条件。改动组装逻辑时必须逐条复核，任一条被破坏都会
退化成某个已发生过的事故。

| # | 不变量 | 违反后果 | 守护测试 |
| --- | --- | --- | --- |
| I1 | 区段顺序固定为 1 → 2 → 3，且不嵌套 | 模型把约束当成任务的一部分 | `test_sections_appear_in_fixed_order` |
| I2 | 用户指令提交后不再出现在后续轮 | 同一条指令被反复提交 | `test_user_section_dropped_once_submitted` |
| I3 | 只带最新一组工具结果 | delta 随轮数单调膨胀；旧结果被当成新事实 | `test_only_latest_tool_results_kept` |
| I4 | 身份声明全局只出现一次 | 模型看到两句同义身份，可能开始回应它 | `test_identity_declared_once` |

### 6.1 第 1 部分与第 2 部分互斥

I2 与 I3 合起来意味着：**常规请求里第 1 部分与第 2 部分不会同时出现**。

- 有工具结果 → 用户指令已提交 → 只有 2（+3）
- 没有工具结果 → 还没有任何执行 → 只有 1（+3）

这不是巧合，是同一个判据的两种表现：*这条 user 有没有已经落进网页会话*。
一旦落进去，它既不该重发（I2），它触发的工具结果也不该在下一轮之后再被重发（I3）。

若两者同时出现，说明输入畸形（客户端把旧 tool 结果与一条新 user 一起发来，
且新 user 之后没有新工具结果）。此时第 2 部分只取最后一条 user 之后的消息，
旧结果被自然排除，不会真的同时输出。

### 6.2 工具结果取「连续段」而非「单条」

I3 说的是「最新一组」，实现取的是**末尾连续的 tool 消息**，不是字面上的最后一条。

理由：模型一次可以输出多个 `tool_call`（并行调用），每个回一条 tool 消息。
只取最后一条会让同组其余调用的结果丢失，模型只能重新发起那些调用——这正好是
「只发最后一条 user」那个事故的同构版本（丢信息 → 重发）。

守护测试：`test_parallel_results_in_latest_group_all_kept`。

## 6.3 坏结构补救（tool_call 生成损坏时重发）

模型声称要调用工具、但那段调用**无法落地**时，需要就地重发。判据问的是
「这次调用能不能变成一次真实调用」，而不是围栏数量。

### 判据一：`tool_call` 围栏未闭合（结构信号）

回复里出现了 ` ```tool_call ` **开围栏**，但后面找不到配对的闭合 ` ``` ` → 判为损坏，
触发重发。

这条判据**独立于 JSON 是否合法**，因为二者会分离：模型写到

````text
```tool_call
{"name": "shell", "arguments": {}}
````

（只有开围栏、没有闭合）就在某个键值后停止输出（页面吞字 / 生成中断），
截断点**恰好是合法 JSON**。
此时「能 `json.loads`」为真，但调用参数很可能残缺，客户端拿到的是一个形状合法、
内容不可信的调用。围栏闭合是更强的结构契约：**开围栏出现就必然要有一个闭合**。

判定规则（`has_unclosed_tool_fence`）：逐对扫描——从每个 ` ```tool_call ` 开围栏
向后找最近的 ` ``` `，找不到即未闭合。只判 `tool_call` 语言围栏；`python` / `bash` /
`json` 等普通代码围栏不参与（正常回答里出现代码块是常态，不能被当成截断）。

两个重发判据（`has_no_usable_call` 整轮、`has_malformed_tool_call` 逐段）都在最前面
先查未闭合，**未闭合优先于 JSON 合法性**。

### 判据二：标记在，但包裹内容不是合法 JSON

回复里出现了 `tool_call` 标记（```tool_call``` 围栏，或裸 `tool_call` 字样），
而包裹的内容**不能** `json.loads` 成一个含非空字符串 `name`、对象型 `arguments`
的 JSON 对象 → 判为损坏，触发重发。具体涵盖：

- 围栏正文为空 / 只有空白（网页端吃掉内容，只剩语言标记）；
- JSON 被截断（括号不闭合、断在半截键名上）；
- JSON 语法错误（括号平衡但内容非法，如 `{name: bash}`、尾逗号、单引号）；
- 解析成非对象（数组、字符串、数字）；
- 缺 `name` / `arguments`，或 `arguments` 不是对象；
- 裸标记后面什么都没有 / 是半截 JSON。

**不看围栏数量，也不看其它语言围栏。** 正常回答里的 `python` / `bash` / `json`
代码块不是调用声明；空围栏做 Markdown 分隔也不是。把它们判成损坏会导致对每个
含代码的答案都白跑一次重发。

### 旧判据（「连续三个空代码围栏」）为何废弃

两个方向都错，各有真实故障：

- **漏判**：网页端把 `tool_call` 围栏内容吃掉、只剩语言标记时一个空围栏都不剩，
  旧判据看不见；JSON 截断同理。表现是 bridge 拿不到调用，客户端收到没法用的正文。
- **误判**：正常回答用空围栏做分隔（```\n```\n```），旧判据判成损坏，白跑一次
  重发还会覆盖正常回答。

新判据直接对齐解析层口径：能 `json.loads` 落地就正常返回（解析交给 parser 层），
落不了地才重发。判据实现见 `glm_web/completion/malformed.py::has_malformed_tool_call`
（`has_empty_fence_triple` 保留为指向它的兼容别名）。

### 整轮判据：好坏混杂不重发（部分成功）

网页端一轮可能同时下达多个调用，其中有的正常、有的格式坏掉。此时**不能因为有一个
坏的就终止整轮**——否则一个好的调用也被连累重发或抛错，会话白白中断。

判据分两层：

- **逐段**：`has_malformed_tool_call(text)` —— 任一标记段非法即 `True`。用于判断
  「这一段调用本身是否可用」。
- **整轮**：`has_no_usable_call(text)` —— 出现了 `tool_call` 标记，但**一个能落地的
  调用都没有**才 `True`。`flow.run_turn` 的重发判据用这一层。

含义：只要一轮回复里至少有一段能 `json.loads` 成合法调用，就**不重发**。好的调用
交给解析层（`parse_tool_calls` 逐段解析、跳过坏段）执行，坏段由模型在下一轮看到
工具反馈后自行补。只有**整轮没有任何可用调用**时才发纯提示词重发。

这与解析层天然一致：`build_tool_calls` 在能解析出至少一个调用时就返回这些调用，
坏的自动被丢弃——整轮判据只是把「adapter 能执行就放行」这个事实提前到 `run_turn`，
避免在 adapter 看到之前就把整轮判死。判据只看结构（能否解析成 `{name, arguments}`
对象），不看工具名是否声明——名字合法性由解析层带 `declared` 判断。

守护测试：`test_mixed_good_and_bad_calls_do_not_retry`（混合不重发）、
`test_all_bad_calls_has_no_usable`（全坏才判坏）、`test_mixed_good_and_bad_calls_has_usable`。

### 两层判据与未闭合的优先级

| 层次 | 函数 | 未闭合时的结论 |
| --- | --- | --- |
| 逐段 | `has_malformed_tool_call` | 直接 `True`（不走 JSON 判定） |
| 整轮 | `has_no_usable_call` | 直接 `True`（不因某段 JSON 合法而放行） |

未闭合是**结构性**损坏，优先级高于「这段内容能不能解析」——因为解析成功不代表
调用完整。混轮场景下（一个闭合正常、一个未闭合），整轮判据仍判坏并重发：
未闭合说明这一轮生成被截断，重发比执行半截调用更安全。

### 重发用纯提示词

重发只发一句 `RETRY_PROMPT`，**不带任何构造信息**——不加 system、不加工具说明、
不加历史回放。原因：带构造信息时模型会把「重发指令」当成新任务的一部分继续跑偏。

只重试有限次（`MALFORMED_RETRIES`）；耗尽后**如实抛出**「结构损坏」，
不静默返回那段没法用的正文。禁用重试（`=0`）时遇到坏回复也直接抛错，不降级为
返回垃圾。这与第 4 节「提交后不重发」不冲突：那条说的是**用户指令**只能提交一次，
这里是模型自己产出的调用坏掉、就地让它重发一次调用，不重新提交用户指令。

### 守护测试

`tests/test_malformed_retry.py`：判据用例覆盖空正文 / 纯空白 / 截断 / 括号不平衡 /
语法非法 / 非对象 / 缺字段 / `arguments` 非对象 / 裸标记空与截断 → 判损坏；
合法围栏调用 / 合法裸标记 / 普通回答 / 其它语言代码块 / 空围栏分隔 / 正文提及该词
→ 不判损坏。

围栏闭合专项：未闭合检测 / 已闭合正常 / 无围栏正常 / 普通代码围栏不参与 /
两个围栏一闭一开判坏 / **JSON 恰好合法但未闭合，两个判据都判坏** /
端到端重发（未闭合 → `RETRY_PROMPT` → 恢复成功）。

行为用例覆盖重发、重试耗尽抛错、禁用重试抛错三组。

## 7. 反模式清单

以下每一种都对应过一次真实故障：

1. 以「最后一条 assistant」为切分点 → 用户补发的格式说明进入本轮，delta 累积膨胀。
2. 只发「最后一条 user」→ 工具结果丢失，模型反复重发同一条工具调用。
3. 扫 `document.body.innerText` 做页面判定 → 历史消息正文里的字面量被误判
   （额度提示、到顶提示都踩过）。判定只扫 chrome 区。
4. 提交后超时重试 → 同一指令在网页会话里被重复提交（`SiteTimeoutError` 只会在
   提交已确认成功之后抛出）。
5. 把格式说明当成任务发出去 → 模型按说明格式回一段调用文本，被当正文返回。
6. 逐条给工具结果加 `[tool result: <name>]` 前缀 → 区段标题已说明语义，前缀冗余。
7. 工具结果返回后仍带第 1 部分 → 用户指令被重发，模型以为用户又说了一遍
   （与第 4 条同源：提交动作只能发生一次，提示词层与提交层各管一头）。
8. 第 2 部分带上全部历史工具结果 → delta 随轮数膨胀；模型把旧结果当成刚发生的事。
9. 第 2 部分只取最后一条 tool → 并行调用的其余结果丢失，模型重发那些调用。
10. system 块注入 `NEUTRAL_IDENTITY` 且第 3 部分又拼 `_PREAMBLE` → 两句同义身份。
11. `include_identity=False` 整段跳过身份替换循环 → 客户端身份断言原样漏进 prompt。
12. 用「连续三个空围栏」判坏结构 → 漏判「只剩语言标记 / JSON 截断」，且误判空围栏分隔。
13. 用存在性正则（有 `name`、括号平衡）判调用是否可落地 → 放过 `{name: bash}`、
    尾逗号等语法非法但括号平衡的调用。判据必须真走一次 `json.loads`。
14. 只按「JSON 能否解析」判坏结构，不看围栏是否闭合 → 截断点恰好是合法 JSON 时
    放行，客户端拿到参数残缺但形状合法的调用。围栏闭合是独立于 JSON 的结构信号，
    必须单独判，且优先级高于 JSON 合法性。
15. 重发时带上 system / 工具说明 / 历史 → 模型把重发指令当成新任务继续跑偏。
16. 重试耗尽后静默返回坏正文 → 客户端拿到没法用的内容，故障被吞掉。应如实抛错。
17. 用逐段判据（任一坏即坏）决定整轮是否重发 → 好坏混杂时误杀已能执行的调用，
    好的调用被连累重发或抛错。整轮重发必须用「一个可用调用都没有」的判据。
18. 注入文本已中性中文，仍保留 `Answer in Chinese.` 补偿句 → 模型把补偿句当任务复述。
    语言/风格补偿句应整句删除。
19. 能力句正则只按行首（`^`+`M`）匹配 → Pi preamble 第二句与身份句同行时匹配不到，
    整句漏进 prompt。句首必须是「行首 或 句号/中文句号/换行之后」。

## 8. 迁移影响（已落地）

本设计相对旧实现的改动，全部已实现：

| 项 | 旧 | 新 |
| --- | --- | --- |
| `delta_prompt` 输出 | 裸文本（user + `[tool result: x]`） | 三区段带标题 |
| `with_tool_instructions` | 把提示拼在 prompt **前面** | 拼成 `[运行环境与要求]` 放**最后** |
| system 消息位置 | 随 `[用户问题]` 之前发出 | 并入 `[运行环境与要求]` 第一块 |
| 工具结果前缀 | 每条 `[tool result: <name>]` | 无前缀，仅区段标题 |
| 工具结果范围 | 最后一条 user 之后的**全部** | 只保留**最新一组**（末尾连续段） |
| 有工具结果时的第 1 部分 | 仍然带上 | **省略**（提交后不重发） |
| `_PREAMBLE` 位置 | `format_tool_instructions` 内部 | `[运行环境与要求]` 内独立一块 |

落地位置：

- `glm_web/prompting.py`：新增 `assemble_prompt()`（三区段组装）、
  `build_context_section()`、`SECTION_USER` / `SECTION_TOOL_RESULTS` / `SECTION_CONTEXT`；
  `delta_prompt(messages, tools=None)` 与 `seed_prompt(messages, budget, tools)` 均转调它。
- `glm_web/tools/prompt.py`：`PREAMBLE` 提升为公开常量，`format_tool_instructions`
  只返回工具格式契约（不再内嵌身份说明）。
- `glm_web/tools/formatting.py`：`render_tool_result` 去掉前缀。
- `glm_web/server.py`：两处调用点把 tools 直接传给 `delta_prompt` / `seed_prompt`，
  不再事后 `with_tool_instructions` 前置拼接。
- 测试：`tests/test_prompt_sections.py` 新增 11 条结构断言；
  `tests/test_prompting.py` / `tests/test_openai_tools.py` 旧断言同步更新。

### 8.1 实现中发现并修正的两个问题

1. **身份说明重复**。`neutralize_system_prompt` 在没有身份断言时会主动插入
   `NEUTRAL_IDENTITY`（「你是一个大语言模型，正在参与一场…」），而第 3 部分又固定拼
   `_PREAMBLE`（「你是一个大语言模型。本次对话…」）——模型会看到两句同义身份。
   修正：第 3 部分的 system 块改用 `include_identity=False`，**只删**客户端的身份断言、
   不再注入中性句；身份声明由 `_PREAMBLE` 单独承担。回归断言见
   `test_identity_declared_once`。
2. **`include_identity=False` 的初版语义过宽**。最初整段跳过身份替换循环，导致
   Pi 的 `You are an expert coding assistant…` 原样漏进 prompt（
   `test_seed_prompt_of_real_pi_system_is_minimal` 捕获）。修正为：仍匹配并删除，
   只是不注入替换句。

## 9. 未决问题

- **超时恢复**：当前 `SiteTimeoutError` 直接抛出，不重试。若要恢复能力，正确做法是
  「续等」而非「重发」——不提交新 prompt，只继续轮询同一会话的回复。尚未实现。
- **多工具结果的呈现**：当前同一组内按出现顺序拼接、空行分隔，不标序号、不标总数。
  若发现模型在多结果场景下分不清哪条对应哪个调用，需要在每条前补工具名或序号——
  但这会部分退回被删掉的 `[tool result: <name>]` 前缀，需权衡。
- **`seed_prompt` 与 I2/I3 的关系**：播种是重放完整历史，天然包含多条 user 与多组
  工具结果，不遵守 I2/I3。这是有意的（网页侧上下文为空，必须靠历史接续），
  但也意味着播种路径不受这两条不变量保护。播种的重放正确性目前只有
  `test_seed_uses_same_section_structure` 覆盖，没有针对「多轮 + 多组结果」的断言。
- **区段标题的模型理解度**：`[用户问题]` / `[工具调用结果]` / `[运行环境与要求]` 这套标题
  尚未在真机上做多轮统计，模型是否会误把标题当正文的一部分（例如在回答里复述
  `[运行环境与要求]`），需要实测。
- **`[运行环境与要求]` 恒存在的影响**：并入 `_PREAMBLE` 后，第 3 部分几乎总会出现。
  若发现模型把它当成「每轮都要回应的内容」，需要把身份说明改成更明确的
  「以下为背景说明，无需回应」。
- **无 user 时的退化形态**：消息里没有 user 也没有 tool 时，组装结果只剩第 3 部分。
  这与「非法形态：只有 3」不同——后者是把格式说明当任务，前者是确实没有任务。
  当前实现允许它（`test_empty_messages_produce_context_only`），但 `server.py` 的
  `prompt.strip()` 检查仍会让它通过，是否应该在无 user 时直接报错，尚未决定。
- **`with_tool_instructions` 的去留**：已无生产调用方，仅为向后兼容保留。
  它在语义上仍可用（把工具契约追加为第 3 部分），但与 `delta_prompt(tools=...)` 重复。
  下一个大版本可以删掉。
- **`render_tool_result` 的 `name` 参数**：前缀去掉后该参数已无用途，函数内 `del name`
  只为保持签名兼容。`glm_web/tools/loop.py::build_tool_results` 仍在按旧格式拼接
  工具结果块，但目前没有生产调用方；两处应一起清理。
- **坏结构判据与解析层的一致性**：当前判据在 `malformed.py` 里用 `json.loads` 独立判一次，
  解析层（`glm_web/tools/parser.py`）再做一次更细的解析。JSON 这一维两处口径目前一致
  （合法 = 能解析成 `{name, arguments}` 对象），但未来若解析层放宽（例如容忍尾逗号），
  判据需同步，否则会出现「判据说坏、解析层其实能读」的重发浪费。理想是判据直接复用
  解析层的 `try_parse` 结果，目前未做。
- **围栏闭合是判据独有的一维**：解析层的 `_FENCE` 正则以 `\Z` 兜底，未闭合时会把剩余
  全文当正文解析——对解析层这是「尽量捞回可用调用」的容错，对判据则是必须拦截的截断。
  二者**有意不同口径**：判据判坏 → 重发；解析层能解析 → 仍可用（用于非重发路径的容错）。
  不要把围栏闭合检查下推进解析层，否则会改变「解析能否成功」的语义。
- **重发的真机有效性**：纯提示词重发在单测里覆盖了调用路径，但「重发一次后模型真的
  输出合法调用」的比率尚未在多轮真机上统计。若重发后仍坏，当前会耗尽 `MALFORMED_RETRIES`
  抛错；是否需要更强的重发提示词或换策略，待实测。
