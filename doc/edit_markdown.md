## 1. 目标与范围

为 DeepseekBridge 增加安全、可控的 Markdown 局部编辑能力，使通过 OpenAI 兼容 API 接入的客户端可以要求 DeepSeek 网页模型提出编辑操作，并在明确启用时由桥接层在本地执行。

核心目标：

- 用明确的起止行号和替换文本编辑文件，避免为小改动重写整份文档。
- 复用现有提示词注入、工具调用解析和坏格式重试机制。
- 默认只生成 diff，不直接写盘；实际写盘必须同时通过请求参数和服务端配置授权。
- 限制目标路径、文件大小和文件类型；编辑前后检查 Markdown 代码围栏结构。
- 写盘前备份，使用临时文件与原子替换，返回结构化执行结果。
- 维持现有 OpenAI 兼容接口和外部工具调用模式，避免已由客户端执行的工具被桥接层重复执行。

本文只规定目标架构、接口、安全边界、实施阶段和验收标准，不代表功能已经落地。

## 2. 当前项目基础与差距

| `deepseek_web/toolcalls.py` | 注入工具调用说明；解析 `tool_call` 围栏、JSON 兜底及 DeepSeek 网页端出现的其他调用格式；将调用转换为 OpenAI `ToolCall` | 继续作为工具调用传输与解析层，不直接承担文件读写 |

| `deepseek_web/streaming.py` | Chat Completions 流式响应与结束原因处理 | 本地执行模式下先缓冲工具轮次，避免把内部工具调用片段当最终答案发送 |
| `deepseek_web/config.py` | 集中读取环境变量和默认配置 | 增加编辑开关、写权限、根目录、备份目录、文件大小与最大执行轮次配置 |
| `tests/test_parsing.py`、`tests/test_malformed.py`、`tests/test_responses.py` | 现有解析、异常与 API 行为测试 | 在原有测试风格上扩展回归测试，并新增 Markdown 引擎和执行器测试 |

### 2.2 当前缺少的部分

当前 `parse_tool_calls()` 将网页模型输出解析为工具名称和 arguments，并在有 `valid_names` 时过滤不在客户端工具列表中的名称。服务端随后把合法调用返回给客户端，通常以 `finish_reason="tool_calls"` 标记。

当前项目没有参考实现中的 `markdown_io.py` 文件编辑引擎，也没有编辑路径沙箱、备份与回滚、diff 生成、Markdown 围栏校验或 `edit_markdown` 本地执行器。现有工具调用解析不等于已具有本地文件编辑能力。

另外，当前解析结果主要保存工具名和 arguments；`to_tool_call_models()` 可以生成新的调用 ID，但并不能假设模型输出中的原始调用 ID 已被完整保留。因此，内部执行流程不能依赖一个尚不存在的稳定调用 ID 来保证幂等。

## 3. 两种执行模式与兼容原则

本功能需要明确区分客户端执行与桥接层本地执行。

### 3.1 外部工具调用模式（现有默认行为）

当 `EDIT_MARKDOWN_LOCAL=false` 时，桥接层不执行本地文件操作。客户端如果提供了名为 `edit_markdown` 的工具 schema，DeepSeek 输出调用后仍按当前 API 契约返回 `tool_calls`，由客户端负责执行并在后续请求发送 `role=tool` 结果。

该模式不得因新增本地编辑模块而改变，也不得把客户端的工具结果误认为桥接层已经执行过。

### 3.2 桥接层本地执行模式（新增，可选）

只有显式启用 `EDIT_MARKDOWN_LOCAL=true` 后，桥接层才将内置 `edit_markdown` 注册为可供模型选择的本地工具，并接管符合条件的调用。

内部流程如下：

1. 根据请求中的 `tools`、`tool_choice` 和服务端配置生成有效工具列表。
2. 在 prompt 中注入准确的工具 schema 和调用格式。
3. 通过现有网页会话获取模型回复，并完成工具格式纠错与解析。
4. 如果本轮全部调用均为桥接层支持的本地 `edit_markdown`，由本地执行器校验和执行。
5. 将执行结果作为新的工具结果消息送回网页模型，继续生成最终回答。
6. 循环达到步数上限或出现需要外部客户端处理的调用时，按定义好的停止策略结束，不能无限循环。
7. 对于已在内部执行的调用，返回最终 assistant 文本，而不是再次返回同一个待执行调用，避免客户端重复执行。

如果同一批调用中混合了本地 `edit_markdown` 和其他外部工具，第一版应将整批调用按现有方式交给客户端，不执行其中任何本地调用。这样可以避免部分执行后又把整批调用返回给客户端造成重复修改。后续如需支持混合批次，必须另行设计明确的分批、关联与失败恢复协议。

### 3.3 工具声明与冲突处理

- `tool_choice="none"` 时不应注入或执行内置工具。
- 仅在本地模式启用、且请求允许选择工具时，才将内置 schema 加入有效工具集合。
- 若客户端也声明了同名 `edit_markdown`，应采用内置 canonical schema 或返回明确的配置冲突错误，不能静默接受不一致的参数定义。
- `valid_names`、prompt 中展示的工具名称和执行器接受的工具名称必须基于同一份有效工具集合。
- 不得扩大现有外部工具的白名单，也不得把未知工具名映射成文件写入命令。
- 现有接口对 `tool_choice` 的处理较为简单；本功能至少必须正确遵守 `none`，其他强制选择语义需结合现有 API 契约单独验证，不能假设已经完全实现。

## 4. 工具契约

### 4.1 Schema

已新增唯一的 `EDIT_MARKDOWN_TOOL` 定义，放在专用的 `deepseek_web/markdown_tools.py` 中，参数如下：

| 参数 | 类型 | 必需 | 含义 |
| --- | --- | --- | --- |
| `path` | string | 是 | 相对于 `EDIT_MARKDOWN_ROOT` 的 Markdown 文件路径 |
| `start` | integer | 是 | 开始行号，1-based，包含此行 |
| `end` | integer | 是 | 结束行号，1-based，包含此行 |
| `new_text` | string | 是 | 用于替换整个 `[start, end]` 区间的文本，可包含换行 |
| `write` | boolean | 否 | 是否请求实际写盘，默认 `false` |

工具名固定为 `edit_markdown`。`start=10, end=12` 表示替换原第 10、11、12 行。第一版只接受合法的现有行区间；文件末尾追加、任意锚点定位、目录批量处理等功能不在范围内。

示例调用：

```tool_call
{"name":"edit_markdown","arguments":{"path":"doc/example.md","start":10,"end":12,"new_text":"替换后的内容","write":false}}
```

示例中的文件名与行号仅用于说明格式，真实调用必须依据当前目标文件的实际内容生成。

### 4.2 写盘语义

`write=true` 仅表达模型请求写盘，不构成授权。最终写盘必须满足：

- 本地执行模式已启用；
- 当前请求允许工具调用；
- 调用名称与参数 schema 合法；
- 目标路径通过沙箱校验；
- 文件能够正常读取、解码并解析；
- 替换区间有效，编辑后结构校验通过；
- `EDIT_MARKDOWN_WRITE=true`；
- 原文件备份成功。

任一必要条件不满足时，不得写盘。仅写权限关闭时，应降级为 dry-run 并返回 diff 和说明；路径非法、结构损坏或备份失败应返回明确错误，不能伪装为成功。

## 7. Markdown 编辑引擎

### 7.1 读取与行模型

`markdown_io.py` 处理 UTF-8 Markdown 文件，并明确保留原始换行与尾换行状态。建议使用字节读取并对文本进行严格 UTF-8 解码，避免文本模式自动转换换行导致选区外内容发生变化。

内部数据结构可保持简单：

- `MdDoc`：原始字节、解码后的文本、行视图、换行信息和围栏索引。
- `Line`：1-based 行号、原始行文本、终止符与所在围栏状态。
- `Fence`：开围栏和闭围栏的行号、标记字符、标记长度与语言信息。
- `Issue`：结构错误代码、说明和相关行号。
- `Backup`：原始文件路径、备份文件路径及所需元数据。

行视图必须保留空行、缩进、行尾空格和换行终止符。编辑选区之外的字节应保持不变；若暂时不能为某类换行形式提供这一保证，应明确拒绝或限定支持范围，并以实测测试为准。

### 7.2 围栏扫描

扫描器使用状态机识别 Markdown 围栏：

- 行首最多允许 3 个空格缩进。
- 支持至少 3 个反引号或波浪号组成的围栏。
- 闭围栏必须与开围栏标记类型相同，且长度不得短于开围栏。
- 4 个空格缩进的代码不视为围栏开头。
- 反引号围栏的信息串不能包含反引号。
- 对未闭合围栏应报告带行号的结构错误，禁止继续写盘。

编辑前扫描原文，编辑后重新解析整个文档。不能只检查 `new_text`，因为替换文本与原文的前后部分拼接后才是最终 Markdown 结构。

第一版允许编辑围栏内部的内容，以支持修改 Markdown 中的代码示例；但编辑结果必须仍然满足结构校验。不能把“围栏可以重新解析”误解为“代码语义正确”或“围栏内部内容保持不变”。

### 7.3 行区间替换

建议实现纯函数 `apply_edit(doc, start, end, new_text)`：

1. 验证 `start`、`end` 为真正的整数，排除布尔值，并要求 `1 <= start <= end <= 行数`。
2. 将替换文本按 UTF-8 编码规则验证；统一替换区间内部采用的换行风格，但保留原文选区外的字节。
3. 保留 `[start, end]` 之外的所有行内容和元数据。
4. 组合新文档，并重新解析 Markdown 围栏。
5. 返回新文档及结构校验结果，不直接访问磁盘。

空字符串允许删除选中的行。对于空文件、无尾换行文件、CRLF 文件、混合换行文件和包含 Unicode 的内容，应制定明确的处理策略并用测试锁定行为，不能依赖系统默认换行转换。

### 7.4 Diff 与备份

- 使用统一 diff 格式向模型和客户端展示前后差异。
- diff 为空时视为无实质更改，不创建多余备份，也不重复写盘。
- dry-run 路径不创建备份或修改目标文件。
- 写盘前创建独立备份；备份文件名使用高精度时间信息或随机唯一后缀，避免连续操作覆盖备份。
- 备份失败立即停止写盘。
- 写入时先在目标文件所在文件系统创建临时文件，完整写入并完成必要的 flush，再通过原子替换更新目标文件。
- 尽可能保留原文件权限等必要元数据；写入或替换失败时清理临时文件，并确保原文件仍可恢复。
- 可以提供单独的 `restore_backup()` 辅助功能，但不能通过模型提供未经校验的备份路径直接进行任意文件覆盖。

## 8. 执行器与安全策略

### 8.1 参数验证

在访问文件系统之前验证全部参数：

- `path` 必须为非空字符串。
- `start` 和 `end` 必须是 JSON integer，不接受字符串数字或布尔值。
- `new_text` 必须是字符串。
- `write` 必须为真正的布尔值；缺省时为 `false`。
- 参数错误返回确定的结构化错误，不依赖 `int()`、`bool()` 之类宽松转换替调用方纠错。

### 8.2 路径沙箱

`resolve_edit_path()` 应实现以下规则：

1. `EDIT_MARKDOWN_ROOT` 解析为绝对路径并作为访问边界。
2. 只接受相对于根目录的路径；拒绝绝对路径、空路径和 `..` 路径段。
3. 解析目标路径并验证其仍位于根目录之内，防止目录穿越和指向外部的符号链接。
4. 拒绝目录、特殊文件及不在允许扩展名范围内的文件；第一版建议只允许 `.md` 与 `.markdown`。
5. 目标应为已存在且可读取的普通文件。新建文件及自动创建任意目录不属于第一版范围。
6. 写入前再次检查目标和根目录关系，缩小检查后目标被替换的竞态窗口。
7. 文件大小不得超过配置上限。

路径检查与实际文件操作必须使用经过校验的解析路径，不能先校验一个路径、再对未经校验的原始输入读写。

### 8.3 权限双门槛

本地执行由 `EDIT_MARKDOWN_LOCAL` 控制，实际写盘由 `EDIT_MARKDOWN_WRITE` 控制。只有本地执行模式开启、工具调用有效且 `write=true` 与服务端写权限同时满足时，才可以修改文件。

建议默认值均为关闭：

- `EDIT_MARKDOWN_LOCAL=false`
- `EDIT_MARKDOWN_WRITE=false`

即使用户请求写盘，服务配置关闭时也不能因提示词、客户端参数或模型自行生成的说明而提高权限。提示词只承担行为引导，真正的安全边界必须由执行代码强制执行。

### 8.4 幂等与失败边界

现有解析器不能保证每一种模型输出都具有稳定的原始调用 ID，因此首版不能宣称已具备跨请求的严格调用幂等性。

首版必须做到：只在完成格式重试后执行一次最终解析出的调用；目标内容未发生变化时跳过写盘与备份；发生任何验证或备份错误时均不写盘。未来若需要强幂等保证，应先定义稳定的 request/call identity，再实现按会话和调用 ID 去重的执行台账，不能仅以参数散列永久缓存结果而误伤后续有意重复的操作。

对于同一请求的内部执行循环，设定最大步数，并保证每一轮只执行通过全部校验的本地工具调用。遇到混合工具批次、未支持的本地工具、格式错误或步数上限时，必须按明确的 API 分支停止或交给客户端；不得无限重试，也不得把已执行调用重新返回给客户端执行。

## 9. 配置设计

以下配置已在 `deepseek_web/config.py` 和 `.env.example` 中实现并说明。

| 配置 | 建议默认值 | 作用 |
| --- | --- | --- |
| `EDIT_MARKDOWN_LOCAL` | `false` | 是否在桥接层内部执行内置 Markdown 工具 |
| `EDIT_MARKDOWN_WRITE` | `false` | 是否授权内置工具实际写盘 |
| `EDIT_MARKDOWN_ROOT` | `PROJECT_ROOT` | 相对路径沙箱根目录 |
| `EDIT_MARKDOWN_BACKUP_DIR` | `output/backups` | 写盘前的备份目录 |
| `EDIT_MARKDOWN_MAX_FILE_BYTES` | `4194304` | 单个 Markdown 文件读取上限，默认 4 MiB |
| `EDIT_MARKDOWN_MAX_STEPS` | `3` | 单个 API 请求允许的内部工具执行轮数上限 |

配置实现应沿用本项目集中读取环境变量的风格，并确保测试可以通过修改 `deepseek_web.config` 属性覆盖值。对无效配置应采用安全默认值或启动时明确报错，不可默默关闭必要的安全限制。

`EDIT_MARKDOWN_ROOT` 应指向最小必要工作区，不应默认扩展到整个用户主目录。备份目录应稳定、可写且具有足够空间；如果允许配置到沙箱外，必须明确其独立信任边界与权限规则。

## 10. 执行结果与错误契约

建议内部执行器统一返回字典，成功示例：

```json
{
  "ok": true,
  "path": "doc/example.md",
  "start": 10,
  "end": 12,
  "write_requested": false,
  "written": false,
  "backup": null,
  "diff": "--- a/doc/example.md\n+++ b/doc/example.md\n..."
}
```

成功结果字段：

| 字段 | 含义 |
| --- | --- |
| `ok` | 执行或预览是否成功 |
| `path` | 已验证的相对路径 |
| `start`、`end` | 实际编辑区间 |
| `write_requested` | 模型是否请求写盘 |
| `written` | 是否实际写盘 |
| `backup` | 备份路径；未写盘时为 `null` |
| `diff` | Unified diff；无变化时为空字符串 |
| `note` | 说明降级、无变更或其他非错误情况，可选 |

失败结果统一使用 `{"ok": false, "error": "..."}`，结构问题可附带 `issues` 数组，每项包含问题代码、说明和行号。错误信息应便于模型理解和修正，但不能泄漏沙箱外的绝对路径、环境变量秘密或不必要的系统信息。

至少区分：参数类型错误、路径越界、文件不存在、文件类型不允许、文件过大、UTF-8 解码失败、原始围栏损坏、行号越界、编辑后结构校验失败、没有写盘权限、备份失败和文件替换失败。

当执行结果返回网页模型时，应作为有边界标记的工具结果消息传入，避免它与用户指令或普通 assistant 文本混淆。播种历史时可使用结果摘要，增量执行时则应保留足够的 diff 和错误细节供模型继续工作。

## 11. API 与流式兼容

### 11.1 Chat Completions

非流式入口先完成生成、工具调用解析与必要的重试，再判断是否进入内部执行流程。若未进入内部执行，保持现有 `ChoiceMessage.tool_calls` 与 `finish_reason` 行为不变。若进入内部执行，则在内部工具循环完成后返回最终 assistant 内容，不向客户端暴露已经执行的调用作为待执行项。

### 11.2 Responses API

Responses API 应通过共享的内部执行服务实现同等行为，不应在 `responses.py` 中重新实现路径校验、围栏解析或备份。输入格式到 ChatMessage 的现有转换方式保持不变，最终响应仍遵循 Responses 的既有结构。

### 11.3 流式请求

工具模式需要先判断最终回复是否包含可用调用。本地执行模式必须确保工具调用被识别之前，不把可能属于内部工具调用的内容不可撤销地发送给客户端。可复用现有缓冲策略；本地执行期间先缓冲内部轮次，只在获得最终 assistant 文本后输出正确的流式事件和结束标记。

必须验证终止原因和事件顺序：已在内部执行的工具调用不能再作为待执行 `tool_calls` 事件发出；正常外部工具调用仍遵循当前流式 API 契约。若关闭缓冲会导致内部调用原文先泄漏给客户端，则在本地执行模式下应强制缓冲，不能允许不一致的半流式行为。

## 12. 提示词与格式约束

继续复用 `format_tools_instruction()` 与 `format_tool_call_emphasis()`，避免新增第二套互相矛盾的格式要求。

注入内容应明确：

- 工具参数必须是符合 schema 的 JSON。
- `start` / `end` 使用从 1 开始的闭区间。
- 替换文本可以包含换行，空字符串表示删除所选行。
- `write=false` 是默认值；请求写盘并不意味着服务器一定允许写盘。
- 工具名称必须逐字匹配 `edit_markdown`。
- 工具调用格式错误时应根据实际报错修正，不要把普通说明文字当成工具执行成功的证据。

提示词不能取代路径沙箱、类型检查或文件写入权限。网页 DOM 会使工具调用输出出现围栏、全角标点或其他兼容格式的问题，应继续依靠 `toolcalls.py` 的解析与 `toolcall_retry.py` 的重试机制处理；不要把文件系统操作直接放入正则解析器。

## 15. 验收标准

功能完成必须同时满足以下条件：

1. 已声明的工具能通过 DeepseekBridge 现有工具提示词机制被模型理解，并可被现有解析器可靠识别。
2. 外部工具模式在默认配置下保持兼容，不执行本地文件操作。
3. 本地模式只接管内置 `edit_markdown` 的合法调用；未知工具和混合工具批次不会被意外部分执行。
4. 默认 dry-run 返回有意义的 diff，且不修改目标文件。
5. 未启用服务端写权限时，任何模型参数都不能强制写盘。
6. 路径穿越、符号链接逃逸、文件大小超限和非法行号均被拒绝。
7. 原始或编辑后 Markdown 围栏损坏时不会写盘。
8. 获准写盘前必须备份；备份失败不会破坏原文件。
9. 写入采用临时文件与原子替换；选区外字节保真由自动化测试证明。
10. Chat Completions、Responses 与流式入口行为一致，不会重复执行内部调用。
11. 相关测试、全量测试、Ruff 和 Harness 检查的实际结果都有记录；未运行的项目标记为未验证。
